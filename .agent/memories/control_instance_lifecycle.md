# agent 驱动引擎：control 实例必须可发现、可停、默认有 deadline

> 2026-09-18，做「agent 开发时不要开一堆长久不关的实例」时定位。汇总为一句：**驱动
> 引擎的入口不拥有实例生命周期，实例就会堆积**。

## 现象

agent 需要自动化/MCP/截图时，各自手搓启动命令：自己挑端口、自己起进程、自己记得 `quit`。
结果同一个 project 上堆了多个 `ya-runtime`，互相抢端口/build 产物，没被关掉的那些一直占
GPU 与端口。第二个/第三个进程还特别难发现——它们照样在跑、照样刷日志，只是没人连它们。

## 四个根因（都在「谁拥有实例」这一层）

1. **没有发现渠道**：没有任何地方记录「谁在跑、端口多少」，于是每个调用者只能重新起一个。
   用 `ps` 反推命令行是启发式，不是状态。
2. **没有上限**：`--exit-after-frame` 只数帧，闲置/卡住的进程永远不会到点。
3. **重复启动静默**：端口被占就自己禁用自动化服务器，进程看起来健康，调用方连不上也看不出
   是「没起好」还是「已经起了」。
4. **harness 杀错进程**：脚本里 `engine.kill()` 杀的是启动器（`ya.py`/`xmake`），引擎是它
   的子进程，父进程死了它照样活。harness 自己被超时打断时，引擎就成了孤儿。

## 现在的契约

- 引擎侧：`ProcessLock` 提供互斥（`project|mode` 一把锁，内核随进程退出/被杀释放）；
  `InstanceRegistry` 把 pid/project/mode/controlPort/启动时间写成记录，供别的进程读。**记录是
  普通文件、锁文件才是独占持有的**——独占文件在 Windows 上连读都读不到，发现数据必须分开存。
- 记录的生命周期跟 claim 绑：product（只有它知道 project/mode）在 `onInit` 写，kernel 在释放
  claim 的同一刻删；夹在中间的窗口里「锁还在、记录已删」比反过来安全（客户端读不到记录时会
  得到明确的拒绝，而不是一个假端口）。
- 工具侧：`Script/ya.py control start` = 有则接入、无则起一个，且默认带墙钟上限；
  `status`/`stop` 负责收残留（记录残留按 pid 存活判断即可清）。
- 所有 Popen 起引擎的地方都传 `--max-lifetime-seconds`，把「父进程死了」变成有界事件。

## 判断规则

- 新增任何「启动引擎的工具/脚本」前先问：它怎么发现已有实例、怎么保证自己死了实例也死。
  两个问题的答案都指向同一个入口，就不要新增第三个启动器。
- 看到两个同 project 实例并存、或者 `control status` 里出现不认识的 pid，先怀疑有绕过 control
  的启动路径，而不是先怀疑锁失效。

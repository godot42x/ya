## 适用场景

- 单个 `.cpp` / `.h` 已经过长，需要按稳定职责拆分
- 模块根目录长期平铺，已经难以导航，需要按功能分子目录
- 现有文件命名不稳定，例如出现 `module.part.cpp` 一类分段命名
- 目标是改善组织、可读性、可维护性，而不是改接口、改行为或顺手优化

## 默认立场

1. 默认不拆；只有当拆分后的可导航性、可解释性明显优于现状时才拆。
2. “大文件”本身不是问题；如果主价值在于能顺着读完整时序、状态流或 owner/facade 主链路，就优先保留。
3. 不要把复杂度从一个文件搬到多个文件；阅读时如果需要频繁跨文件来回跳转，通常说明拆分收益不够。
4. 若问题主要来自声明臃肿、内部 helper 混杂、命名失真，优先先收敛头文件和内部结构，而不是立刻物理拆文件。

## 判断是否需要拆分

1. 文件超过约 1500 行时，只说明“值得检查”，不自动等于“应该拆”。
2. 同一文件里如果混有多个稳定功能块，例如 facade、导入逻辑、反射、GUI、事件路由、离屏任务，且这些块能被独立理解，才适合拆开。
3. 如果代码的主要价值在于一眼看完整执行顺序、状态机分支或资源时序，就先不要拆主链路。
4. 如果拆出去后仍然高度互相 include、职责说不清，或者读主流程需要连续跨多个实现文件跳转，就先不要拆。
5. 若只是不喜欢大文件、想顺手“更整齐”，但没有明确导航收益，就不要动。
6. 这份 skill 只处理“物理组织重构”：移动文件、拆分文件、目录归类、修 include；不顺手改接口、算法、状态流。

## 拆分粒度与命名规则

1. 文件名按类名或稳定职责命名，例如 `AppLifecycle.cpp`、`ModelImportAssimp.cpp`、`ShaderReflection.cpp`。
2. 不要使用 `App.Lifecycle.cpp`、`AssetManager.Texture.cpp`、`module.part.cpp` 这类分段命名。
3. facade / owner 保留在模块根目录；专属 helper、导入器、阶段实现放进稳定子目录。
4. 若需要共享内部声明，可使用 `*Internal.h`，但只放内部辅助类型和内部约定，不把新的公共接口塞进去。
5. `.cpp` 拆分后，要同步检查 `.h` 是否也应收敛声明，避免实现拆了、头文件仍然臃肿。
6. 拆分后的文件应尽量让读者按“根入口 -> 单次跳转 -> 细节实现”理解；不要把一个连续主流程切成多段散落在多个同级 `.cpp`。

## 目录组织规则

1. 先按功能域分目录，再在目录内按类或职责命名文件。
2. 根目录优先保留外部入口、facade、owner、公共状态定义。
3. 子目录优先表达稳定职责，例如：`Lifecycle/`、`GUI/`、`Utility/`、`Manager/`、`Texture/`、`Meta/`。
4. 不要为了短期任务创造临时目录名；目录名要能承载未来同类文件继续收敛。
5. 如果模块已经有既有分层，优先沿用当前风格，不再平行造一套新分法。
6. 新目录若只承载一两个彼此强耦合的文件，且没有后续扩展预期，通常说明不值得为它增加一级导航层。

## 执行步骤

1. 先读现有文件，列出其中的职责块和它们的边界。
2. 先判断主阅读路径：读者是否需要在一个地方看到完整时序；若需要，先保住这条主链路。
3. 先命名目标文件和目录，再开始搬移代码，避免边搬边想导致反复改名。
4. 先搬不改：优先保持函数签名、调用顺序、状态流和已有日志不变。
5. 再修引用：统一更新 `#include`、前向声明、命名空间引用和构建路径。
6. 若拆分引入新的中间文件，确认它们是稳定职责，而不是一次性过渡物。
7. 完成后再整体复查 diff，确认没有混入无关逻辑改动，也没有把主链路打碎。

## include 路径与构建更新

1. 文件移动后，优先全局检查旧 include 路径是否还残留。
2. 如果模块外部引用了旧路径，要一起修；不要只修当前目录内的 include。
3. 新子目录落地后，确认 `xmake` 的源文件收集仍覆盖这些路径。
4. 需要时运行 `python3 Script/ya.py cfg` 或 `xmake project -k compile_commands` 刷新 clangd 与导航。
5. 完成后至少执行一次构建验证，优先 `python3 Script/ya.py build` 或 `python3 Script/ya.py build --project <path>`。

## 验证清单

1. `git diff` 主要由文件移动、重命名、include 修正、必要声明迁移组成。
2. 没有顺手抽新接口、改状态机、改资源时序、改业务逻辑。
3. 构建通过；若有测试入口，再补最小必要测试验证。
4. 拆出的每个文件都能用一句话解释其稳定职责。
5. 目录结构比改动前更清晰，而不是把复杂度从一个文件搬到多个难懂文件。
6. 读主流程时，不需要在多个同级实现文件之间反复横跳才能拼出完整时序。
7. 如果改完后自己更难解释“从入口到关键状态变化是怎么走的”，说明这次拆分大概率失败。

## 常见错误模式

1. 借拆分名义顺手重写接口或行为，导致任务越界。
2. 使用 `module.part.cpp` 命名，拆完仍然没有稳定职责语义。
3. 只拆 `.cpp`，忘了同步整理 `.h` 中的声明和依赖。
4. 机械按行数切割，拆出多个互相强耦合、无法独立理解的文件。
5. facade、owner、helper 混放，导致目录层级更乱。
6. 为了“看起来更模块化”把主链路拆碎，结果阅读时必须在多个文件之间来回拼图。
7. 新建子目录或 helper 文件只是转移视觉体积，没有实质降低理解成本。
8. 只修本目录 include，遗漏跨模块引用，最后在 unity build 或全量构建里爆炸。
9. 大块搬迁/删除用 sed 行号操作，导致误删函数或循环（见
   `.agent/memories/module_split_sed_regression.md` 与
   `terrain_processor_active_pump_regression.md`）；删除后必须核对函数与
   循环清单（`rg -n "activeEntities|ClassName::"` 对比 HEAD）。

## 模块 target 拆分标准（2026-08-09 定稿，计划决策 14-A..14-E）

拆 target 前先保证职责清晰和高内聚；只有存在独立复用、独立裁剪、独立
生命周期或明确依赖隔离价值时才拆。模块内先通过子目录 + 接口 + private
include 保持边界；某 feature 同时满足下列条件中**至少两个**才升级为独立
target：

1. 有真实独立裁剪需求；
2. 能形成闭合依赖、不反向引用主模块；
3. 有独立初始化/关闭/资源生命周期；
4. 有独立测试目标；
5. 拆分能显著减少 package/shader/编译闭包；
6. 未来可能被替换或独立复用。

每次模块调整（拆分/合并/改名）必须先更新计划中的模块 charter（为什么
独立、对外提供什么、禁止依赖什么），再动代码；不允许先建 target 后补理由。

## 边界与构建核查清单（拆分/归位后必查）

1. 公共转发头必须由**所属模块**公开：`xmake show -t <target>` 后逐个确认
   模块公开的每个转发头确实属于该模块。同目录多个 target 时小心
   `./include` 相对路径陷阱（如 backend-common 与 ya-rhi-vulkan 同在
   Backend/ 目录，`./include` 会解析到同一位置，导致头从错误的 target
   泄漏出去）。
2. 删除模块级 `ya_engine_defines()` 前先确认该模块所有头只用自己的
   `YA_*_API` 宏（`rg -o "YA_[A-Z_]+_API" <模块目录>` 应只有一种）。
3. 生命周期回调必须在最后一个强引用释放**之前**发出；以引用形式传入成员
   shared_ptr 的函数，reset 前先想清楚别名语义（见
   `.agent/memories/scenemanager_on_scene_destroy_alias_bug.md`）。
4. 依赖环要区分"真实环"与"潜在环"：先确认当前依赖方向（`xmake show -t`
   的 deps 列表），潜在环可通过归属决策规避，不必强行重构。
5. xmake 3.0.8 一次 `xmake b` 只接受一个 target；脚本里多 target 必须
   拆成逐 target 调用。
6. 冒烟必须覆盖真实消费路径（如含 TerrainComponent 的场景 + 自动化
   stable 判定），不能只靠单测和"能编译"。

## 停止线

1. 如果你已经能清楚解释当前大文件的主链路，但拆完后反而要靠文件名猜流程，就停止。
2. 如果拆分收益主要体现在“单文件变短”，而不是“职责和导航更清晰”，就停止。
3. 如果拆分会让 facade/owner 失去作为阅读入口的价值，就停止。
4. 如果没有一句明确的话能说明“为什么拆完比现在更容易读”，就停止。

## 相关 skills

- `cpp-style`：命名、最小改动、文件与目录收敛规则的直接来源
- `render-arch`：拆渲染相关代码时判断该留在抽象层、runtime 编排层还是后端层
- `material-flow`：拆材质与资源消费链路时判断 authoring/runtime/pipeline 边界
- `resource-system`：拆 resolve、handle、dirty queue 等资源相关逻辑时一起看
- `debug-review`：拆分完成后做 diff 自检、边界复盘和提交前检查
- `ya-build`：目录迁移后检查构建入口、目标和生成链路

## 退出条件

- 目标文件或目录已经按稳定职责收敛
- 没有引入新的功能变化或无关抽象
- include 与构建路径已经修正干净
- 构建验证通过，且 diff 边界清晰可解释
- 主链路仍然容易顺着读，拆分收益大于跳转成本

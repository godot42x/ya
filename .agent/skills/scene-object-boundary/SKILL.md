# Scene Object Boundary (generated vs authored)

Use this skill before adding anything that *generates* entities for an existing
object: a gizmo, an icon, a body mesh, an instanced sub-object, a runtime cache
node. It states which layer owns that thing and how far the ownership reaches.

## Vocabulary

- **Host** — the entity the author placed in the scene. It carries the authored
  components (`CameraComponent`, `PointLightComponent`, `ModelComponent`).
- **Companion** — an entity generated *for* a host. It is not authored content:
  no scene file row, no clone, no inspector writes.
- **Authored content** — components and entities that the scene file stores and
  the user owns.
- **Derived visual** — something that only exists to be looked at (camera body,
  light icon, model mesh).

ECS in YA is flat: an `entt::entity` is a handle, and the registry stores no
parent/child relation. **Hierarchy lives only in the NodeTree** (`Scene::_nodeMap`
maps handle to `Node`). So "child entity" means: a second flat entity whose `Node`
is parented under the host's node. That is what makes a companion follow the host
transform for free, and why companion components never track position themselves.

## Three archetypes and their boundaries

1. **Companion entity.** Generated by a host system. Carries
   `ManagedChildComponent{host}` and lives as a child node of the host.
   Not serialized, not cloned, rebuilt on load. Examples: model mesh children,
   camera body, light icon.
2. **Derived topology + authored payload.** Generated by a rule but carrying a
   genuine authoring field. `RenderComponent` is the live example: it is created
   by `MaterialRenderLinkageRule` yet holds `RenderingLayer`, which *is* the
   author's decision, and the scene file stores it. The rule must adopt an
   existing instance and overwrite only the derived fields. Do not "clean up"
   such a component by deleting it; mark the derived fields
   `.transient()` / `.notSerialized()` instead.
3. **No identity of its own.** A projection of host state drawn per frame by an
   overlay (camera frustum lines, light direction gizmo). Do not make it a
   component; read the host and draw.

## Rules

1. **Provenance is declared, never inferred.** A companion's kind, editor
   editability and packing class are stated once, for the *host type*, in that
   host's `CompanionSpec` (`CompanionRegistry`). Never decide provenance from an
   asset path, an entity name, or "does this component look generated".
2. **One lifecycle driver.** `CompanionManager` (an `ILinkageRule`) connects the
   host signals, sweeps hosts that already exist on scene init, and keeps exactly
   one companion per host alive while the host component is present. Do not add a
   per-host-type rule class; add a declaration.
3. **Derived visuals are not persisted, and the host is the only rebuild
   input.** `SceneSerializer` skips companions by marker presence
   (`exclude<ManagedChildComponent>`), `Scene::clone` skips them too, and load
   rebuilds them from the host's components. Never store a companion's asset path
   as the thing that identifies it.
4. **Visibility is a per-view feature bit, not component state.** `ERenderFeature`
   bits live on the *item* (`RenderDrawItem.features`, `BillboardComponent.features`)
   and views declare `viewFeatures`; `RenderFrameExtractor::prepareView`'s bucket
   binding is the single filter, so GBuffer, Forward, shadow and the entity-id
   pick pass agree by construction. Companions exist in every mode (dev builds
   keep them, a future pack filter may strip them); only the view decides what is
   drawn. Never bake a view policy into a shared scene snapshot.
5. **Generated rows are visible but not editable.** They stay selectable so the
   user can see what an object carries, but the inspector fields are read-only,
   there is no transform manipulator, and structural commands are refused. A
   companion that is editable is a lie: the reconciler overwrites it.
6. **User-facing visibility is not editor visibility.** `BillboardComponent::bVisible`
   is a content switch; companion membership is provenance. Do not derive one from
   the other.
7. **Undeclared companions default to `Content` and remain editable.** Model mesh
   children depend on this: they are ordinary content with transform editing.
8. **Companions do not change the collision/physics contract.** No collision, no
   decals, no shadow contribution unless the view asked for their feature set.
9. **A component is created with its owner, not fixed up afterwards.**
   `IComponent::_owner` is what lets a component read the entity that holds it
   (`CameraComponent::getFreeView` resolves the owner's world pose from it);
   ownership is therefore an argument to the single creation funnel
   (`detail_component_mutation::addComponent`) and every path that emplaces a
   component passes the `Entity*`. A funnel that creates a component without an
   owner is a silent-wrong-pose bug, not a missing feature: the component falls
   back to a default and the mesh, the view and the wireframe drawn from it
   disagree while only one of them is right. Never create-then-patch: patch is
   forgettable, an argument is not.
10. **A sprite animation with a non-empty atlas drives derived sprite fields that stay in the scene file.** `SpriteAnimationComponent` writes the host `Sprite2DComponent`'s `image` path and `uvRect` when the set's `atlas` is set. Those values are derived and are still serialized. An empty `atlas` leaves the sprite texture alone on purpose, so one sheet layout can skin several sprites.
11. **Scene files omit reflected fields that still equal `T{}`.**
   `SceneSerializer` compares a component's reflection JSON with the reflection
   JSON of a default-constructed instance and drops equal fields. Objects
   recurse, including `__base__`; an object that becomes empty is removed;
   arrays compare as a whole. The component key itself stays, even as `{}`.
   Custom output (`useReflectionSerialization() == false`, for example
   `LuaScriptComponent`) is not trimmed. A missing field means the code
   default, so changing a component default changes how old scenes load.

## Anti-patterns

- Putting a derived visual on the *host's own* component slot (a camera's
  `StaticMeshComponent` used for its gizmo body). It costs the host its slot and
  forces per-consumer special cases in serializer, inspector, clone, extraction
  and picking.
- A boolean like `bManagedByLight` that encodes provenance on the component
  instead of in the declaration.
- Pushing a view policy (e.g. `bAppStopped`) into the shared scene snapshot.
- Generating children from inside `paint` / layout callbacks.
- `Entity::getComponent<T>()` on a path where `T` may be absent — **it asserts in
  debug and aborts the editor**. Use `Entity::tryGetComponent<T>()` (or
  `hasComponent<T>()` first) whenever presence is a question. This is not
  theoretical: an unconditional `getComponent<ModelComponent>()` in the
  inspector's instance notice aborted the editor on selecting any camera, light
  or empty, because only model instances carry that component.

## Checklist for a new generated object

1. Which host component type generates it? Add one `declareHost<THost>` with a
   `CompanionSpec` in the composition root (`AppLifecycle`).
2. Is it content or an editor gizmo? That picks `kind`, and with it the feature
   bits and the editor editability.
3. Does it need host-transform refresh beyond what the node hierarchy gives?
   Set `bFollowsHostTransform` (light icons do, for orientation) and refresh in
   `onUpdateHost`.
4. Does it need geometry? Point a normal `StaticMeshComponent` at engine
   content (`Engine:Content/Editor/Gizmos/...`) with `setModelPath`. Engine
   gizmos are ordinary mesh sources: the same resolve/material features work, and
   the path lives in the declaration rather than in scene data, so it is still
   swappable without a scene migration.
5. Add a test that it is not serialized, that removing the host component removes
   it, and that a `Game`-only view does not draw it when it is a gizmo.
